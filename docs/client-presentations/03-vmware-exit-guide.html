Migration Phases

A phased approach minimizes risk and maintains uptime.

1

Assessment (Week 1-2)

Inventory all VMs. Classify by criticality (dev/staging/production). Identify dependencies. Estimate disk sizes. Map network requirements. Run pre-flight checks with hyper2kvm.

2

Pilot Migration (Week 3-4)

Migrate 5-10 non-critical VMs (dev/test). Validate conversion quality. Test boot success. Verify application functionality. Build team confidence and document process.

3

Staging Migration (Week 5-8)

Migrate staging environments. Test with real workloads. Validate performance. Set up monitoring. Create runbooks for common issues. Batch process with YAML automation.

4

Production Migration (Week 9-16)

Migrate production VMs in maintenance windows. Use queue-based batch processing. Verify each VM boots and passes health checks. Maintain VMware as rollback for 30 days.

5

Decommission VMware (Week 17-20)

After 30-day parallel run, decommission vSphere. Cancel VMware licenses. Reclaim hardware. Document lessons learned. Celebrate savings.

Target Architecture

Choose your landing zone based on workload needs.

🖥️

Option A: KVM + libvirt

Best for: Traditional IT, existing Linux admin teams, simple VM workloads.

  • RHEL/Fedora with KVM + libvirt
  • Cockpit web UI for management
  • virt-manager for desktop admin
  • Live migration between hosts
  • Lowest complexity, fastest adoption
☸️

Option B: KubeVirt on Kubernetes

Best for: Cloud-native teams, mixed VM+container workloads, GitOps.

  • VMs as Kubernetes resources
  • Same tooling for VMs and containers
  • Helm charts, operators, CI/CD
  • Multi-cluster, multi-cloud capable
  • Path to eventual containerization
🏗️

Option C: OpenShift Virtualization

Best for: Enterprise Red Hat shops, need vendor support + SLA.

  • Red Hat supported KubeVirt
  • Integrated with OpenShift platform
  • MTV (Migration Toolkit for Virtualization)
  • Enterprise support contracts
  • Certified, hardened, tested
🌐

Option D: Hybrid (Recommended)

Best for: Large estates with mixed requirements.

  • Critical VMs on KVM/libvirt (simple, reliable)
  • Cloud-native workloads on KubeVirt
  • Edge sites on K3s + KubeVirt
  • hyper2kvm deploys to both targets
  • Migrate once, deploy anywhere
