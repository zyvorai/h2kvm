3. Technical Approach

Q: Describe your technical approach to converting VMware VMs to KVM format.
Our conversion pipeline uses h2kvm's VMCraft engine (pure Python + qemu-nbd), which processes each VM through these stages:
  • Export: govc-based vSphere export with streaming progress monitoring
  • Convert: VMDK/OVA → QCOW2 with optional compression (40-60% space savings)
  • Fix: Automated offline modifications — VirtIO drivers (Windows), initramfs rebuild (Linux), fstab UUID conversion, GRUB update, network configuration
  • Deploy: Generate libvirt domain XML with NUMA-aware CPU pinning, hugepages, VirtIO devices, and correct UEFI/BIOS firmware detection
  • Validate: Automated boot test, service verification, and performance baseline comparison
No manual intervention required for standard Linux and Windows VMs. Custom handling documented for edge cases (vendor appliances, legacy OS).
Q: How do you handle Windows VMs and prevent BSOD?
Windows BSOD (0x7B INACCESSIBLE_BOOT_DEVICE) is the #1 migration failure mode. h2kvmctl prevents this by:
  • Mounting the guest disk offline using qemu-nbd
  • Loading the Windows SYSTEM registry hive
  • Injecting VirtIO storage drivers (viostor/vioscsi) as boot-critical
  • Injecting VirtIO network drivers (NetKVM) and balloon drivers
  • Supporting Windows Server 2012 R2 through 2025, and Windows 10/11
We carry the latest virtio-win.iso (from Fedora) with pre-tested drivers for all supported Windows versions. Zero BSOD guarantee with our process.

Q: How do you handle rollback if a migration fails?
Rollback is immediate and zero-risk:
  • Source VMware VMs are never modified or deleted during migration
  • VMware VMs remain powered off (not deleted) for 48 hours after cutover
  • Rollback = power on VMware VM, power off KVM VM (2-minute process)
  • MAC addresses are preserved, so network/DHCP/DNS require no changes
  • Decision deadline: 2 hours after go-live per wave
  • We have achieved 0% rollback rate across our last [N] migration projects due to thorough pre-testing
Q: What is the expected downtime per VM during migration?
Typical downtime: 5-15 minutes per VM. Our process pre-converts VMs while they are still running on VMware. The cutover window involves only: (1) clean shutdown of VMware VM, (2) boot KVM VM. The conversion itself runs hours or days before the cutover, so it does not contribute to downtime. For large databases requiring consistency, we recommend a 2-4 hour window that includes final backup verification.

Appendix A: Detailed Technical Q&A

Q: What disk formats are supported for conversion?
VMDK (all sub-formats: monolithic sparse, monolithic flat, split sparse, stream-optimized), OVA, OVF+VMDK, VHD, VHDX, RAW, QCOW2. Source format is auto-detected.
Q: How are VM network configurations preserved?
MAC addresses are preserved from OVF metadata, ensuring DHCP leases, license servers, and monitoring continue without changes. Network topology (VLAN assignments) is mapped to Linux bridge or OVS configurations. h2kvmctl auto-generates libvirt network XML from OVF NetworkSection.
Q: Can you migrate VMs with snapshots?
Yes. VMware snapshot chains are consolidated during export (govc export produces a flat image). The resulting image contains the latest state including all snapshots. We recommend consolidating snapshots in VMware before export for fastest processing.
Q: How do you handle UEFI vs BIOS boot VMs?
h2kvmctl auto-detects firmware type by examining the partition table (GPT = UEFI, MBR = BIOS) and OVF metadata. UEFI VMs use OVMF firmware (edk2-ovmf package). Secure Boot is supported with enrolled keys. Windows 11 VMs additionally get a virtual TPM 2.0 (swtpm).
Q: What monitoring replaces vCenter after migration?
We deploy Prometheus + Grafana + Alertmanager (all open-source, $0 cost) with pre-built dashboards for KVM host metrics, per-VM resource usage, capacity forecasting, and alerting. Optional: Loki for log aggregation (replaces vRealize Log Insight). Web-based management via Cockpit (included with RHEL/Rocky).
Q: How does KVM high availability compare to vSphere HA?
Pacemaker + Corosync provides equivalent automatic VM restart on host failure. With shared storage (Ceph or NFS), VMs are restarted on surviving hosts within 30-60 seconds. Live migration (virsh migrate --live) provides vMotion-equivalent functionality with sub-100ms downtime. Both 2-node (with quorum device) and 3+ node clusters are supported.
Q: Can you migrate to KubeVirt (Kubernetes) instead of standalone KVM?
Yes. h2kvmctl supports direct deployment to KubeVirt via the CDI (Containerized Data Importer). Converted QCOW2 images are uploaded as PersistentVolumeClaims, and VirtualMachine resources are created in the target namespace. This enables running VMs and containers on the same Kubernetes cluster with unified kubectl management, monitoring, and networking.
Q: What is the ongoing cost of running KVM vs VMware?
KVM (kernel module) and libvirt are included in every Linux distribution at no cost. Optional: RHEL subscription ($799/host/year) for vendor support, or use Rocky Linux / AlmaLinux for $0. There are no per-VM fees, no per-core fees, no per-socket fees, and no forced bundles. Hardware upgrades (more cores, more RAM) never increase software costs.
