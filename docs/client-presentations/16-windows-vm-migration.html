The Windows BSOD Problem

Why Windows VMs crash after migration — and how h2kvm prevents every failure mode.

Without proper driver injection, every Windows VM will BSOD on first boot

Windows loads storage drivers at boot from the registry. VMware uses LSI Logic/PVSCSI, Hyper-V uses storvsc, AWS uses Xen/NVMe. KVM uses VirtIO. If VirtIO drivers aren't pre-installed in the offline disk image, Windows cannot access the boot volume and crashes with INACCESSIBLE_BOOT_DEVICE (0x7B). This is the #1 Windows migration failure — h2kvm eliminates it completely.

Multi-Stage Pipeline

h2kvm uses a 3-stage approach for safe, reliable Windows migration.

Stage 1 Bootstrap
→
Stage 2 Driver Injection
→
Stage 3 Cleanup & Verify

Stage 1 Bootstrap

  • Mount Windows disk offline via qemu-nbd
  • Detect Windows version (2016/2019/2022/2025/10/11)
  • Detect boot mode (BIOS vs UEFI)
  • Detect current storage controller (LSI/PVSCSI/storvsc)
  • Locate Windows registry hives (SYSTEM, SOFTWARE)
  • Identify installed hypervisor tools
  • Map partition layout (EFI System, Recovery, C:)
  • Select correct VirtIO driver version for OS

Stage 2 Driver Injection

  • Extract VirtIO drivers from virtio-win ISO
  • Copy viostor/vioscsi .sys + .inf to C:\Windows\drivers
  • Copy NetKVM .sys + .inf for network
  • Copy Balloon .sys + .inf for memory
  • Load offline SYSTEM hive, add driver registry entries
  • Set VirtIO storage driver to boot-start (Start=0)
  • Update CriticalDeviceDatabase for VirtIO PCI IDs
  • Configure UpperFilters/LowerFilters for storage stack

Stage 3 Cleanup & Verify

  • Remove VMware/Hyper-V/cloud agent services
  • Remove source hypervisor drivers from driver stack
  • Update BCD for new boot disk controller
  • Enable serial console (COM1) for headless access
  • Generate libvirt XML with VirtIO + Q35 machine
  • Generate KubeVirt manifest (optional)
  • Automated boot test: start VM, verify no BSOD
  • Webhook notification on success/failure

How KVM Reduces SQL Server Licensing

The VMware Problem

  • VMware vSphere reports all physical cores to Microsoft
  • SQL Server per-core licensing counts cores on the host
  • A 2-socket, 16-core host = 32 cores to license
  • Even if SQL VM uses only 4 vCPUs, you may need to license all 32 cores
  • SQL Server Standard: $3,945/core = $126,240 per host
  • SQL Server Enterprise: $15,123/core = $483,936 per host

The KVM Advantage

  • KVM with CPU pinning exposes only assigned cores
  • SQL VM with 4 pinned vCPUs = license only 4 cores
  • NUMA-aware placement for performance + compliance
  • cgroups enforce CPU isolation — verifiable by auditors
  • SQL Server Standard: $3,945 x 4 = $15,780
  • SQL Server Enterprise: $15,123 x 4 = $60,492
