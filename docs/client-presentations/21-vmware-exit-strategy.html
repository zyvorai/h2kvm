The 5-Phase Exit Plan

A structured, risk-minimized approach. Each phase has clear gates before proceeding.

1

Phase 1 Discovery & Assessment (Week 1-2)

Connect to vCenter read-only. Discover all VMs with CPU, RAM, disk, OS, power state. Classify by tier (dev/staging/prod). Identify Windows VMs needing VirtIO. Map network dependencies. Run h2kvmctl doctor on target hosts. Estimate total migration time. Output: VM inventory spreadsheet + migration complexity report.

2

Phase 2 Pilot (Week 3-4)

Migrate 5-10 non-critical VMs (dev/test). Use zkvm TUI for guided migration. Validate: boot test passes, applications work, network reachable, performance acceptable. Document issues and fixes. Build team confidence. Gate: All pilot VMs boot and pass health checks.

3

Phase 3 Staging & Batch Testing (Week 5-8)

Migrate staging/QA environments (20-50 VMs). Use YAML automation for batch processing. Test with real workloads. Set up Prometheus/Grafana monitoring on KVM hosts. Create runbooks for common issues. Validate Windows VMs (SQL Server, AD, Exchange). Gate: Staging passes full regression testing.

4

Phase 4 Production Migration (Week 9-16)

Migrate production VMs in planned maintenance windows. Batch 10-20 VMs per wave. Use job scheduling (hypersdk) for off-peak hours. Boot verification on every VM. Keep VMware running in parallel for 30 days. Webhook notifications to Slack/Teams. Gate: All production VMs running on KVM for 30 days with zero issues.

5

Phase 5 Decommission VMware (Week 17-20)

After 30-day parallel run, decommission vSphere. Cancel VMware/Broadcom licenses. Repurpose or retire ESXi hardware. Remove vCenter, vSAN, NSX. Document lessons learned. Report savings to leadership. Result: $0 VMware cost from this point forward.

Pre-Flight Validation

  • h2kvmctl doctor checks 9 areas on target hosts:
  • Disk space (sufficient for conversion)
  • KVM support (cpu virtualization enabled)
  • qemu-img and qemu-nbd installed
  • libvirt running and accessible
  • virtio-win ISO available (for Windows VMs)
  • Network bridge configured
  • kubectl + KubeVirt (if deploying to K8s)
  • govc installed (for vSphere export)
  • Run on every target host before migration day

What hyper2kvm Does Automatically

  • Exports VMDK from vCenter via govc
  • Converts VMDK → QCOW2 with compression
  • Linux VMs: Rebuild initramfs (VirtIO), fix fstab (UUID), fix GRUB, remove VMware Tools, SELinux relabel
  • Windows VMs: Inject VirtIO drivers (viostor, NetKVM, Balloon), fix registry, fix BCD, remove VMware Tools
  • Generates optimized libvirt domain XML
  • Runs virsh define to register VM
  • Starts VM and verifies boot (no BSOD/panic)
  • Reports pass/fail per VM

Target Architecture

Four landing zones — choose based on your team's skills and workload requirements.

Option A: Pure KVM + libvirt

  • Best for: Traditional IT, existing Linux teams
  • RHEL/Fedora/Ubuntu + KVM (in kernel)
  • libvirt for VM lifecycle management
  • Cockpit web UI for browser-based admin
  • virt-manager for desktop admin
  • Live migration between hosts (shared storage)
  • Cost: $0 software
  • Complexity: Lowest
  • hyper2kvm: emit_domain_xml: true

Option B: K3s + KubeVirt

  • Best for: Cloud-native teams, edge sites
  • K3s: single binary, 512MB RAM
  • KubeVirt: VMs as K8s pods
  • GitOps with ArgoCD/Flux
  • Same tooling for VMs + containers
  • Edge-ready (single-node deployable)
  • Cost: $0 software
  • Complexity: Medium
  • hyper2kvm: deploy_k8s: true

Option C: OpenShift Virtualization

  • Best for: Red Hat shops wanting vendor support
  • OpenShift + OpenShift Virtualization
  • Red Hat supported KubeVirt
  • MTV available (but hyper2kvm is more flexible)
  • Enterprise support contracts + SLAs
  • Certified, hardened, tested
  • Cost: $50K+/yr (OpenShift subscription)
  • Complexity: High

Option D: Hybrid (Recommended)

  • Best for: Large estates, mixed requirements
  • Critical/simple VMs → KVM/libvirt
  • Cloud-native workloads → K3s + KubeVirt
  • Edge sites → K3s (single-node)
  • hyper2kvm dual-target: same conversion, both outputs
  • emit_domain_xml: true + deploy_k8s: true
  • Cost: $0 software
  • Complexity: Medium
  • Maximum flexibility

Workload-Specific Migration Strategies

Database Servers

  • Stop DB before export (consistency)
  • Or take VMware snapshot (crash-consistent)
  • Migrate secondary/replica first
  • Verify replication on KVM
  • Promote KVM replica, then migrate primary
  • VirtIO SCSI for best I/O performance

Active Directory DCs

  • Never migrate all DCs at once
  • Migrate secondary DCs first
  • Verify AD replication (repadmin)
  • Then migrate primary (FSMO holder)
  • Test: DNS, Kerberos, Group Policy
  • VirtIO injection handles boot

Clustered / HA Workloads

  • Migrate passive/secondary node first
  • Test failover to KVM node
  • Then migrate active/primary node
  • Pacemaker: update resource config
  • WSFC: adjust quorum settings
  • Oracle RAC: use rolling migration
