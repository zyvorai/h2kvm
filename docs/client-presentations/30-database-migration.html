The Database Migration Challenge

Database VMs carry the most risk — and the biggest savings opportunity.

Why databases are different from other VMs

Databases have active writes, transaction logs, replication relationships, and strict consistency requirements. A naive VM migration (shutdown → export → convert → boot) causes downtime. A crash-consistent snapshot may lose transactions. The strategy depends on the database engine and acceptable downtime window.

Per-Database Best Practices

PostgreSQL

  • Preferred: Streaming replication to KVM replica, then promote
  • Cold: pg_ctl stop -m fast before export
  • Snapshot: Safe — WAL replay recovers from crash-consistent state
  • Post-migration: Verify pg_isready, check replication lag
  • VirtIO performance: Comparable to PVSCSI for OLTP workloads
  • Tip: Separate WAL on second VirtIO disk for best I/O

MySQL / MariaDB

  • Preferred: MySQL replication to KVM replica, then promote
  • Cold: mysqladmin shutdown before export (clean shutdown)
  • Snapshot: InnoDB crash recovery handles inconsistency
  • GTID replication: Set up replica on KVM, catch up, promote
  • Post-migration: SHOW SLAVE STATUS, check binary log position
  • Tip: innodb_flush_log_at_trx_commit=1 for safety

SQL Server

  • Preferred: Always-On AG — add KVM replica, failover
  • Cold: Stop SQL Server service before export
  • VirtIO injection: hyper2kvm handles automatically
  • Licensing win: KVM CPU pinning reduces per-core licensing 20-40%
  • Post-migration: Verify databases online, AG health, agent jobs
  • Tip: Lock pages in memory + large pages on KVM for performance

Oracle Database

  • Preferred: Data Guard to KVM standby, switchover
  • Cold: shutdown immediate before export
  • Snapshot: Redo log replay recovers crash-consistent state
  • RAC: Migrate one node at a time (rolling migration)
  • Post-migration: Verify SELECT STATUS FROM V$INSTANCE
  • Tip: ASM disk groups migrate with the VM disk

SQL Server Licensing Savings

The biggest hidden win of database migration: reduced per-core licensing costs on KVM.

The VMware SQL Server Licensing Problem

On VMware

  • VMware vSphere exposes all physical cores to the guest
  • Microsoft licensing may count all host cores
  • A 2-socket, 16-core/socket host = 32 cores to license
  • SQL Standard: $3,945/2-core pack x 16 = $63,120
  • SQL Enterprise: $15,123/2-core pack x 16 = $241,968
  • Even if SQL VM uses only 4 vCPUs

On KVM (with CPU pinning)

  • KVM with CPU pinning exposes only assigned cores
  • SQL VM with 4 pinned vCPUs = license only 4 cores
  • NUMA-aware placement for performance + compliance
  • cgroups enforce CPU isolation — verifiable by auditors
  • SQL Standard: $3,945 x 2 = $7,890
  • SQL Enterprise: $15,123 x 2 = $30,246
