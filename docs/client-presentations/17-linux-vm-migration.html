The Linux Boot Problem

Why Linux VMs fail to boot after migration — and how h2kvm prevents every failure.

Without initramfs rebuild and fstab repair, most Linux VMs fail to boot on KVM

Linux loads storage drivers from the initramfs at boot time. VMware VMs use vmw_pvscsi or mptscsi. Hyper-V uses hv_storvsc. AWS uses xen-blkfront or nvme. KVM needs virtio_blk / virtio_scsi. If VirtIO drivers aren't in the initramfs, the kernel can't mount the root filesystem and drops to an emergency shell — or panics. Meanwhile, fstab entries referencing /dev/sda or /dev/xvda break because KVM presents disks as /dev/vda.

initramfs Rebuild — Distro-Specific Commands

# RHEL / Rocky / Alma / Fedora / CentOS / Oracle Linux / Photon / SUSE (dracut-based):
chroot /mnt/guest dracut --force --add-drivers "virtio_blk virtio_scsi virtio_net virtio_pci" /boot/initramfs-$(uname -r).img $(uname -r)

# Ubuntu / Debian (initramfs-tools-based):
echo -e "virtio_blk\nvirtio_scsi\nvirtio_net\nvirtio_pci" >> /mnt/guest/etc/initramfs-tools/modules
chroot /mnt/guest update-initramfs -u -k all

# h2kvm handles all of this automatically — detects distro, selects correct method, runs in chroot

Enterprise Linux Workloads

Critical applications migrated safely with h2kvm.

PostgreSQL / MySQL / MariaDB

  • Data directories migrate with disk — no dump/restore
  • InnoDB/WAL files intact on target
  • VirtIO SCSI provides comparable I/O to PVSCSI
  • Tablespaces on separate partitions handled via fstab fix
  • Replication resumes after boot (update source IP)
  • Tip: Stop DB before export for consistency, or use snapshot

Docker / Podman Hosts

  • Container images in /var/lib/docker migrate with disk
  • Overlay2/fuse-overlayfs storage intact
  • Docker daemon starts on boot, containers resume
  • Podman rootless containers preserved
  • Container registry data (Harbor, GitLab) migrates with volume
  • Tip: docker-compose stacks auto-restart via systemd

Kubernetes Nodes

  • kubelet, containerd, etcd data migrates with disk
  • K8s control plane: migrate workers first, then masters
  • etcd snapshot recommended before control plane migration
  • CNI plugins (Calico, Cilium) need network reconfiguration
  • PersistentVolumes on local disks travel with the VM
  • Tip: Cordon + drain node before migration

Web Servers (Apache / Nginx)

  • Simplest migration — standard pipeline, no special handling
  • Virtual hosts, SSL certs, .htaccess all preserved
  • Let's Encrypt certs in /etc/letsencrypt intact
  • PHP-FPM, Python WSGI, Node.js apps unchanged
  • Load balancer health checks resume automatically
  • Tip: Verify DNS and IP bindings post-migration

NFS / Samba File Servers

  • Exported filesystems migrate with disk
  • NFS exports in /etc/exports preserved
  • Samba shares in smb.conf intact
  • POSIX ACLs and extended attributes preserved on ext4/XFS
  • Clients reconnect after DNS/IP update
  • Tip: Update /etc/exports for new network if IP changes

Monitoring (Prometheus / Grafana / ELK)

  • Prometheus TSDB data in /var/lib/prometheus intact
  • Grafana dashboards in SQLite/PostgreSQL preserved
  • Elasticsearch indices on data volumes travel with disk
  • Alertmanager configs and templates preserved
  • Large data volumes: ensure target has sufficient I/O
  • Tip: VirtIO SCSI + NVMe backend for heavy I/O

GitLab / Jenkins CI

  • Git repositories, CI data, artifacts migrate with disk
  • GitLab PostgreSQL + Redis data intact
  • Jenkins workspace and job history preserved
  • SSH keys and deploy keys in /home/*/.ssh intact
  • Runner registrations: re-register with new IP
  • Tip: GitLab backup before migration as safety net

FreeIPA / LDAP / Kerberos

  • LDAP directory (389-ds) data migrates with disk
  • Kerberos keytabs and principal database preserved
  • CA certificates in /etc/pki intact
