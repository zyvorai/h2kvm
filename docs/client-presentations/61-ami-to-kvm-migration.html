What is AMI Migration?

Amazon Machine Images are not portable by default. h2kvm makes them portable.

The Problem

  • AMIs are locked to AWS EC2 — no native "download" button
  • AWS export produces raw disk images with cloud-specific drivers
  • Cloud-init expects metadata service at 169.254.169.254
  • Boot configuration targets cloud-specific disk controllers
  • GRUB references cloud device names (xvda, nvme0n1)
  • No VirtIO drivers in cloud kernels (not needed on EC2)

The h2kvm Solution

  • Accept raw/VMDK/VHD/qcow2 from any cloud export
  • Auto-detect OS: Linux distro, version, boot mode
  • Rebuild initramfs with virtio_blk, virtio_scsi, virtio_net
  • Fix GRUB root= for new disk device topology
  • Stabilize fstab (UUID/PARTUUID, no /dev/xvda)
  • Emit libvirt XML + smoke test — one command

Single Command Migration

From cloud image download to running KVM VM in one pipeline.

Step 1: Download the AMI

# Photon OS AMI (publicly available)
wget https://packages.vmware.com/photon/5.0/GA/ami/photon-ami-5.0-dde71ec57.x86_64.tar.gz
tar xzf photon-ami-5.0-dde71ec57.x86_64.tar.gz

# AWS EC2 export (private AMIs)
aws ec2 export-image --image-id ami-0123456789 --disk-image-format RAW \
  --s3-export-location S3Bucket=my-exports,S3Prefix=ami-export/

Step 2: Migrate with h2kvm

sudo h2kvmctl \
  --cmd local \
  --vmdk photon-ami-5.0-dde71ec57.x86_64.raw \
  --out-format qcow2 --compress \
  --fstab-mode stabilize-all \
  --regen-initramfs \
  --emit-domain-xml \
  --libvirt-test \
  --vm-name photon-ami \
  --memory 2048 --vcpus 2

Step 3: Deploy Permanently

sudo virsh define out/libvirt/photon-ami.xml
sudo virsh start photon-ami
sudo virsh domifaddr photon-ami   # Get IP address

Automated Offline Fixes

What h2kvm does to make a cloud image boot on KVM.

1. Initramfs Rebuild

Cloud kernels lack VirtIO modules. h2kvm chroots into the guest and runs dracut -f with virtio_blk, virtio_scsi, virtio_net, and nvme drivers. The kernel boots with the right storage and network drivers from the first attempt.

2. GRUB Boot Repair

Cloud images reference /dev/xvda or /dev/nvme0n1p3. h2kvm updates root= in grub.cfg to match the new VirtIO disk topology (/dev/vda3). BLS entries and GRUB defaults are both handled.

3. fstab Stabilization

Device names change between cloud and KVM. h2kvm converts all fstab entries to UUID or PARTUUID, adds nofail flags, and removes cloud-specific mount points. The system mounts cleanly on any hardware.

4. Network Configuration

Cloud network configs reference cloud-specific NIC names. h2kvm detects NetworkManager, systemd-networkd, or netplan configs and ensures they work with VirtIO network devices. DHCP continues to work out of the box.

Migration Architecture

How h2kvm processes cloud images with the VMCraft engine.

VMCraft Engine

  • Pure Python + qemu-nbd + Linux tools
  • No libguestfs dependency required
  • Direct NTFS/ext4/XFS/btrfs mount
  • LVM, LUKS, mdraid support
  • Python hivex for Windows registry
  • Containerized LVM scans (Podman)

Disk Processing Pipeline

  • Format detection: RAW, VMDK, VHD, qcow2, OVA
  • Split VMDK support (twoGbMaxExtentSparse)
  • Sparse-to-qcow2 pre-conversion for reliability
  • Compressed output with qemu-img
  • Image validation (qemu-img check)
  • Checksum generation (SHA256)

Boot Repair

  • UEFI & BIOS auto-detection
  • GRUB2 + BLS config patching
  • dracut / initramfs-tools rebuild
  • VirtIO module injection
  • Serial console configuration
  • OVMF firmware auto-selection

Deployment

  • Libvirt domain XML generation
  • virsh define + smoke test
  • KubeVirt manifest generation
  • Dual deploy: libvirt + Kubernetes
  • VNC/SPICE graphics auto-detection
  • Health check with IP wait

Key Technical Innovation: Cached VirtIO ISO Extraction

h2kvm extracts virtio-win.iso once using bsdtar (Rock Ridge aware) and caches the result at /var/lib/h2kvm/virtio-win-extracted/. Subsequent Windows migrations reuse the cache instantly. The Rock Ridge filesystem extension preserves long directory names (w11, w8.1) that ISO 9660 truncates.
