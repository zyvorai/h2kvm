Right-Size Calculator

# right-size.py — calculate optimal sizing
import json

def right_size(vm_data):
    """Calculate right-sized resources from usage data."""
    cpu_p95 = vm_data['cpu_p95_percent'] / 100
    mem_p95 = vm_data['mem_p95_gb']

    # CPU: P95 usage * allocated + 50% headroom
    optimal_cpu = max(2, round(
        cpu_p95 * vm_data['allocated_vcpus'] * 1.5
    ))

    # Memory: P95 usage + 25% headroom, round to nearest 2GB
    optimal_mem = max(2, round(
        mem_p95 * 1.25 / 2
    ) * 2)

    # Storage: actual used + 50% growth
    optimal_disk = round(
        vm_data['disk_used_gb'] * 1.5
    )

    return {
        'vcpus': optimal_cpu,
        'memory_gb': optimal_mem,
        'disk_gb': optimal_disk
    }

NUMA-Aware VM Placement

Proper NUMA placement prevents 40% performance penalties on multi-socket servers.

NUMA Architecture

# Typical 2-socket server NUMA topology
# Node 0: CPU 0 (cores 0-31), 256 GB local RAM, PCIe slots 1-4
# Node 1: CPU 1 (cores 32-63), 256 GB local RAM, PCIe slots 5-8
#
# Local memory access: ~80ns
# Remote memory access: ~140ns (75% slower!)
#
# Rule: Keep VM's vCPUs and memory on the SAME NUMA node

# Check NUMA topology
numactl --hardware
# node 0: cpus 0-31, size 262144 MB
# node 1: cpus 32-63, size 262144 MB
# node distances:
#   node 0 1
#     0: 10 21   ← 21 = 2.1x latency to remote node

# Bad placement (crosses NUMA boundary):
virsh vcpupin db-server 0 0    # NUMA 0
virsh vcpupin db-server 1 32   # NUMA 1 ← CROSS-NODE!

# Good placement (all on NUMA 0):
virsh vcpupin db-server 0 0
virsh vcpupin db-server 1 1
virsh vcpupin db-server 2 2
virsh vcpupin db-server 3 3
virsh numatune db-server --nodeset 0 --mode strict

NUMA Placement Rules

Small VMs (< 16 vCPU, < 64 GB)

  • Fit within a single NUMA node
  • Pin all vCPUs to cores on same NUMA node
  • Pin memory to same NUMA node
  • Multiple small VMs can share a NUMA node
  • Max ~4 small VMs per NUMA node (avoid contention)
  • Performance: optimal (100% local memory access)

Large VMs (> 32 vCPU, > 256 GB)

  • Must span NUMA nodes (too large for one)
  • Use numatune --mode interleave for balanced access
  • Or use vNUMA: expose NUMA topology to guest OS
  • <numa><cell cpus='0-15' memory='131072'/><cell cpus='16-31' memory='131072'/></numa>
  • Guest OS then optimizes memory allocation per-NUMA
  • Required for: large databases, in-memory analytics

Enable TRIM/Discard in Guest VMs

Add discard='unmap' to libvirt disk XML and run fstrim -av periodically in guests (or enable continuous TRIM with discard mount option in fstab). This returns unused blocks to the QCOW2 image, keeping actual disk usage minimal. Schedule weekly fstrim via cron for best results.

CPU Selection

  • Intel Xeon Scalable (Sapphire/Emerald Rapids): best single-thread, proven VMware migration path
  • AMD EPYC (Genoa/Bergamo): best core count per dollar, 96-128 cores/socket
  • Rule: Intel for latency-sensitive, AMD for density
  • Always: match CPU family across cluster for live migration
  • Enable: VT-x/AMD-V, VT-d/IOMMU in BIOS

Memory Selection

  • DDR5-4800+: required for latest Xeon/EPYC
  • ECC: mandatory for production (error correction)
  • Populate evenly: same DIMMs per channel per socket
  • Don't overcommit: RAM is the #1 bottleneck for VMs
  • Reserve: 10% for host OS + KVM overhead
  • Hugepages: allocate 80% of host RAM as 2MB hugepages

Migration-Time Right-Sizing

Apply right-sizing during migration — the best time to change VM resources.

h2kvmctl Right-Sizing During Conversion

# Right-size during migration (set new resource allocation)
h2kvmctl convert \
  --source db-server.vmdk \
  --format qcow2 --compress \
  --fix-all \
  --emit-domain-xml \
  --deploy-libvirt \
  --memory 8192 \    # Was 16384 on VMware (only used 5GB)
  --vcpus 4 \        # Was 8 on VMware (only used 1.8 cores)
  --network-bridge br-db

# Batch right-sizing from analysis spreadsheet
# migration-rightsized.yaml
vms:
  - name: db-server
    source: { vmdk: /data/db-server.vmdk }
    deploy:
      memory: 8192    # Right-sized from 16384
      vcpus: 4         # Right-sized from 8
      network_bridge: br-db

  - name: web-server
    source: { vmdk: /data/web-server.vmdk }
    deploy:
      memory: 2048    # Right-sized from 8192
      vcpus: 2         # Right-sized from 4
      network_bridge: br0

Right-Sizing Safety Net

  • KVM makes it easy to adjust after migration
  • Add CPU: virsh setvcpus vm 6 --config (reboot)
  • Add RAM: virsh setmem vm 12G --config (reboot)
  • CPU hotplug: virsh setvcpus vm 6 --live (no reboot!)
  • Memory hotplug: virsh setmem vm 12G --live (if guest supports)
  • Start conservative, scale up if monitoring shows need
  • Set alerts at 80% utilization for proactive scaling
