The Licensing Problem

  • Windows Server Datacenter: Required for unlimited VMs per host — $6,155 per 2-core pack, minimum 8 packs per server = $49,240 per host
  • Windows Server Standard: Only 2 VMs per license — need multiple licenses for more VMs
  • System Center: Additional $3,607 per 2-core pack for management
  • SQL Server on Hyper-V: Must license all physical cores on host
  • CALs: Per-user or per-device Client Access Licenses on top
  • Total: A 4-host Hyper-V cluster can cost $200K+ in Microsoft licensing alone

The Technical Limitations

  • Windows-only hosts: Hyper-V requires Windows Server OS on the host
  • SCVMM complexity: System Center Virtual Machine Manager is expensive and complex
  • Limited Linux support: Linux VMs work but are second-class citizens
  • No KubeVirt path: No native container/VM convergence
  • Vendor lock-in: VHD/VHDX format, Hyper-V IC dependencies, Microsoft ecosystem
  • No edge story: Windows Server is too heavy for edge deployments

Export Methods

Method 1: Direct Copy (Simplest)

  • Shut down VM on Hyper-V
  • Copy VHD/VHDX file from Hyper-V storage
  • Default location: C:\Users\Public\Documents\Hyper-V\Virtual Hard Disks\
  • Transfer via SMB share, SCP, or USB drive
  • Works for any Hyper-V version
  • Best for: Small number of VMs, simple setup

Method 2: Hyper-V Export

  • Right-click VM in Hyper-V Manager → Export
  • Exports VM config + VHD/VHDX + snapshots
  • PowerShell: Export-VM -Name "vm01" -Path "D:\exports"
  • Preserves checkpoint chain
  • h2kvm auto-flattens checkpoints
  • Best for: VMs with checkpoints/snapshots

Method 3: hypersdk (Automated)

  • hypersdk connects to Hyper-V via WinRM or SSH
  • Discovers VMs with metadata (CPU, RAM, disks)
  • Exports VHD/VHDX programmatically
  • Streaming progress with ETA
  • Batch export multiple VMs
  • Best for: Large estates, automated pipelines

Method 4: Azure VM Export

  • Azure VMs use Hyper-V internally
  • hypersdk exports via managed disk snapshot → SAS URL
  • Downloads VHD format
  • Same Hyper-V IC removal + VirtIO injection
  • Plus: removes Azure waagent
  • Best for: Azure-to-on-prem repatriation

Windows on Hyper-V → KVM

The most common Hyper-V migration scenario — Windows Server VMs moving to KVM.

Without VirtIO injection, Windows VMs from Hyper-V will BSOD on KVM

Windows boots with storvsc.sys (Hyper-V synthetic storage). KVM uses VirtIO. Without pre-injecting VirtIO drivers into the offline disk, Windows can't see the boot volume and crashes with INACCESSIBLE_BOOT_DEVICE (0x7B). h2kvm handles this automatically.

Enterprise Workloads & Scenarios

Active Directory Domain Controllers

  • NTDS.dit and SYSVOL migrate with disk
  • Migrate secondary DCs first, verify replication
  • VirtIO injection handles boot on KVM
  • DNS zones and Kerberos keytabs intact
  • Critical: Never migrate all DCs simultaneously

SQL Server

  • Database files migrate with disk — no reinstall
  • VirtIO SCSI provides excellent I/O performance
  • KVM CPU pinning reduces per-core licensing
  • Always-On AG: migrate secondary replicas first
  • Savings: Eliminate Datacenter + reduce SQL cores

File Servers / DFS

  • NTFS permissions (ACLs) fully preserved
  • DFS namespaces and replication intact
  • SMB shares auto-start after boot
  • Deduplication volumes migrate correctly
  • Simplest migration — standard pipeline

Linux Web/DB on Hyper-V

  • Apache/Nginx, PostgreSQL/MySQL — standard fixes
  • initramfs rebuild + fstab + GRUB fix
  • Remove Hyper-V IC daemons
  • Bonus: Move host OS from Windows to Linux too
