CPU & Memory Optimization

Pin vCPUs to physical cores and use hugepages for predictable, low-latency performance.

CPU Pinning with virsh vcpupin

Why CPU Pinning Matters

  • Without pinning: vCPUs float across physical cores (cache misses)
  • With pinning: each vCPU locked to a specific physical core
  • Eliminates cross-NUMA memory access (up to 40% latency reduction)
  • Required for SQL Server per-core licensing optimization
  • Prevents noisy-neighbor effects in multi-VM hosts
  • Improves real-time workload jitter from ~100us to ~10us

Implementation

# Check NUMA topology
lscpu | grep -i numa
numactl --hardware

# Pin vCPUs in libvirt XML
<vcpu placement='static'>4</vcpu>
<cputune>
  <vcpupin vcpu='0' cpuset='2'/>
  <vcpupin vcpu='1' cpuset='3'/>
  <vcpupin vcpu='2' cpuset='4'/>
  <vcpupin vcpu='3' cpuset='5'/>
  <emulatorpin cpuset='0-1'/>
</cputune>

NUMA Topology Awareness

# Example: 2-socket server with 16 cores/socket
# NUMA node 0: cores 0-15, memory 128GB local
# NUMA node 1: cores 16-31, memory 128GB local

# BAD: VM vCPUs split across NUMA nodes (cross-node memory access penalty: 40-70ns)
<vcpupin vcpu='0' cpuset='0'/>   # NUMA 0
<vcpupin vcpu='1' cpuset='16'/>  # NUMA 1  <-- cross-node!

# GOOD: All vCPUs on same NUMA node, memory allocated locally
<numatune>
  <memory mode='strict' nodeset='0'/>
</numatune>
<vcpupin vcpu='0' cpuset='2'/>   # NUMA 0
<vcpupin vcpu='1' cpuset='3'/>   # NUMA 0
<vcpupin vcpu='2' cpuset='4'/>   # NUMA 0
<vcpupin vcpu='3' cpuset='5'/>   # NUMA 0

Hugepages Configuration

2MB Hugepages (Standard)

# Allocate 16384 x 2MB = 32GB
echo 16384 > /proc/sys/vm/nr_hugepages

# Persistent: /etc/sysctl.conf
vm.nr_hugepages = 16384

# Libvirt XML
<memoryBacking>
  <hugepages>
    <page size='2048' unit='KiB'/>
  </hugepages>
</memoryBacking>

Disk I/O Optimization

VirtIO disk configuration, I/O schedulers, and cache modes for maximum throughput.

VirtIO Multiqueue for High-IOPS Workloads

# Enable multiqueue VirtIO-blk (one queue per vCPU)
<disk type='file' device='disk'>
  <driver name='qemu' type='qcow2' cache='none' io='native' discard='unmap'/>
  <source file='/var/lib/libvirt/images/vm-disk.qcow2'/>
  <target dev='vda' bus='virtio'/>
  <driver queues='4'/>  <!-- Match vCPU count -->
</disk>

# VirtIO-SCSI multiqueue (better for many disks)
<controller type='scsi' model='virtio-scsi'>
  <driver queues='4' iothread='1'/>
</controller>

# IOThreads — dedicated threads for disk I/O (off main QEMU thread)
<iothreads>2</iothreads>
<iothreadpin iothread='1' cpuset='6'/>
<iothreadpin iothread='2' cpuset='7'/>

Disk Cache Modes

cache='none' (Recommended for Production)

  • Guest I/O goes directly to host filesystem (O_DIRECT)
  • No host page cache duplication (saves RAM)
  • Best for databases: fsync actually hits disk
  • Requires io='native' for async I/O
  • Safe with guest filesystem journaling (ext4, xfs)
  • Comparable to VMware's "eager zeroed thick" performance

cache='writeback' (Best Throughput)

  • Host page cache absorbs writes (faster, less safe)
  • Data loss risk on host crash (not guest crash)
  • Good for: build servers, CI/CD, disposable VMs
  • NOT safe for databases unless battery-backed controller
  • Combined with io='threads' for best results
  • 30-50% better write throughput than cache='none'

cache='writethrough' (Safest)

  • Every write flushed to disk before acknowledging guest
  • Slowest option but zero data loss risk
  • Appropriate for: financial systems, compliance workloads
  • Not recommended unless regulatory requirement
  • 50-70% slower writes than cache='none'
  • Reads still benefit from host page cache

discard='unmap' (Thin Provisioning)

  • Guest TRIM/discard operations punch holes in QCOW2
  • Reclaims space when guest deletes files
  • Essential for QCOW2 thin provisioning to stay thin
  • Guest: fstrim -av or mount with discard option
  • Host: passes through to NVMe/SSD TRIM
  • Minor CPU overhead per discard operation

Network Performance

vhost-net, multiqueue, and TCP offloading for near-native network throughput.

vhost-net Acceleration

How vhost-net Works

  • Default VirtIO-net: packets go through QEMU userspace (slow path)
  • vhost-net: kernel module handles data path directly
  • Bypasses QEMU for packet processing (kernel-to-kernel)
  • Reduces CPU usage per Gbps by ~50%
  • Enabled by default on modern libvirt/QEMU
  • Verify: lsmod | grep vhost_net

VirtIO-net Multiqueue

# Libvirt XML: enable multiqueue
<interface type='bridge'>
  <source bridge='br0'/>
  <model type='virtio'/>
  <driver name='vhost' queues='4'/>
</interface>

# Inside guest: activate all queues
ethtool -L eth0 combined 4

# Verify
ethtool -l eth0
cat /proc/interrupts | grep virtio

TCP Offloading & Tuning

# Host: verify offloading on bridge/tap
ethtool -k tap0 | grep -E "tcp-segmentation|generic-receive|scatter-gather"
# tcp-segmentation-offload: on
# generic-receive-offload: on
# scatter-gather: on

# Guest: kernel tuning for high throughput
sysctl -w net.core.rmem_max=16777216
sysctl -w net.core.wmem_max=16777216
sysctl -w net.ipv4.tcp_rmem="4096 87380 16777216"
sysctl -w net.ipv4.tcp_wmem="4096 65536 16777216"
sysctl -w net.core.netdev_max_backlog=5000
sysctl -w net.ipv4.tcp_congestion_control=bbr

# Guest: increase ring buffer size
ethtool -G eth0 rx 1024 tx 1024
