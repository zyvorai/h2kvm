Offline Media Transfer Workflow

USB/HDD sneakernet with encrypted disk images, checksums, and chain-of-custody.

End-to-End Sneakernet Process

# STEP 1: Export VMs on source network (VMware side)
h2kvmctl export --source vsphere --server vcenter.classified.mil \
  --vm "db-server,app-server,web-frontend" \
  --output /mnt/transfer-media/ \
  --encrypt --passphrase-file /root/transfer-key.gpg \
  --checksum sha256 --manifest

# STEP 2: Verify checksums before physical transfer
h2kvmctl verify --manifest /mnt/transfer-media/manifest.json
# Output: 3 VMs verified, 47.2 GB total, SHA-256 checksums match

# STEP 3: Physical transfer (write-blocker → encrypted USB → courier)
# Chain-of-custody form signed by: exporter, courier, importer

# STEP 4: Import on destination network (KVM side)
h2kvmctl import --source /mnt/transfer-media/ \
  --decrypt --passphrase-file /root/transfer-key.gpg \
  --verify-checksums \
  --output /var/lib/libvirt/images/ \
  --convert qcow2 --compress \
  --emit-domain-xml --deploy-libvirt

Transfer Media Options

Encrypted USB 3.2 SSD (Recommended)

  • Hardware: IronKey D500S or Apricorn Aegis Padlock
  • Capacity: 1-8 TB, hardware AES-256 encryption
  • Transfer speed: 1 GB/s (USB 3.2 Gen 2)
  • FIPS 140-3 Level 3 certified (IronKey)
  • Tamper-evident: epoxy-filled, brute-force self-destruct
  • 50 VMs at 50 GB avg = 2.5 TB → 1x 4TB drive, ~42 min transfer

Data Diode Transfer (Highest Security)

  • Hardware: Owl Cyber Defense DualDiode or Waterfall Security
  • One-way transfer: physically impossible to exfiltrate
  • Throughput: 100 Mbps - 10 Gbps depending on model
  • h2kvmctl streams VM data through diode protocol
  • Receiving side reassembles and verifies checksums
  • Required for: cross-domain (e.g., UNCLASS → SECRET)

Manifest & Chain of Custody

  • manifest.json: VM name, size, SHA-256, timestamp, exporter ID
  • GPG-signed manifest prevents tampering during transport
  • DD Form 1149 or equivalent for physical media tracking
  • Two-person integrity (TPI) for classified media handling
  • Media sanitization after transfer: DoD 5220.22-M or degauss
  • Audit log: who exported, who transported, who imported

Encryption Options

  • LUKS2 full-disk: cryptsetup luksFormat /dev/sdX
  • GPG per-file: gpg --symmetric --cipher-algo AES256
  • h2kvmctl --encrypt: uses AES-256-GCM with PBKDF2
  • FIPS mode: fips-mode-setup --enable on RHEL/Rocky
  • Key management: HSM or split-knowledge passphrase
  • At-rest + in-transit encryption for complete chain

RPM/DEB Package Bundling

Pre-staging all dependencies for offline installation on target hosts.

Building Offline RPM Repository

# On internet-connected staging machine (same OS version as target)
# Download all KVM/libvirt packages and dependencies
dnf download --resolve --destdir=/mnt/offline-repo/ \
  qemu-kvm libvirt libvirt-client virt-install virt-viewer \
  libguestfs-tools python3-libvirt bridge-utils \
  edk2-ovmf swtpm swtpm-tools

# Download hyper2kvm and its Python dependencies
pip download -d /mnt/offline-repo/python/ \
  pyyaml lxml requests tqdm paramiko

# Create repository metadata
createrepo_c /mnt/offline-repo/

# Copy to transfer media
cp -r /mnt/offline-repo/ /mnt/transfer-media/repo/

Target Host Installation (Offline)

# On air-gapped target host
# Mount transfer media
mount /dev/sdX1 /mnt/transfer-media

# Add offline repo
cat > /etc/yum.repos.d/offline-kvm.repo <<'EOF'
[offline-kvm]
name=Offline KVM Repository
baseurl=file:///mnt/transfer-media/repo
enabled=1
gpgcheck=0
EOF

# Install everything offline
dnf install --disablerepo='*' --enablerepo=offline-kvm \
  qemu-kvm libvirt libvirt-client virt-install

# Install hyper2kvm
pip install --no-index --find-links=/mnt/transfer-media/repo/python/ hyper2kvm

# Verify installation
h2kvmctl doctor --offline

Loading into Air-Gapped Registry

Harbor Registry (Recommended)

  • Deploy Harbor offline installer (500 MB bundle)
  • Self-signed TLS certs (no external CA needed)
  • LDAP/AD integration for auth (air-gapped AD)
  • Vulnerability scanning with offline CVE DB
  • Load images: skopeo copy oci-archive:kubevirt.tar docker://harbor.local/kubevirt/virt-operator:v1.3.0
  • Image replication between air-gapped sites

K3s Embedded Registry

  • K3s supports pre-loading from /var/lib/rancher/k3s/agent/images/
  • Place tar files: cp kubevirt-images.tar /var/lib/rancher/k3s/agent/images/
  • K3s auto-imports on restart (no registry needed)
  • Simplest option for single-node or small clusters
  • No registry infrastructure to maintain
  • Add --private-registry for multi-node with local registry

  • CDI (Containerized Data Importer) needs local source
  • Upload via virtctl image-upload from local file
  • virtctl image-upload pvc vm-disk --size=50Gi --image-path=disk.qcow2
  • Or use DataVolume with registry source pointing to Harbor
  • Pre-convert with h2kvmctl, then upload converted QCOW2
  • Supports QCOW2, raw, VMDK formats

Conversion in Disconnected Mode

h2kvmctl performs all conversion operations locally without any network access.

Offline Conversion Pipeline

# Full offline conversion — no network calls at any stage
h2kvmctl convert \
  --source /mnt/transfer-media/exported-vms/db-server.vmdk \
  --output /var/lib/libvirt/images/ \
  --format qcow2 \
  --compress \
  --offline \
  --virtio-drivers /mnt/transfer-media/drivers/virtio-win.iso \
  --fix-fstab \
  --fix-initramfs \
  --emit-domain-xml \
  --deploy-libvirt

# What --offline does:
# 1. Disables all network checks (DNS, NTP, package repos)
# 2. Uses local VirtIO drivers instead of downloading
# 3. Rebuilds initramfs using only installed kernel modules
# 4. Skips online activation checks for Windows VMs
# 5. Uses local timezone data instead of NTP sync

Security Controls

Two-Person Integrity (TPI)

  • Media export requires two authorized personnel
  • Split-knowledge passphrase: each person holds half
  • Manifest signed by both exporter and verifier
  • Chain-of-custody log with timestamps and signatures
  • Media sealed in tamper-evident bags for transport
  • Import verification by two different personnel

Audit Trail Without SIEM

  • Local syslog: all h2kvmctl operations logged
  • JSON-structured logs for post-migration analysis
  • Log rotation with integrity checksums (SHA-256)
  • Export logs to removable media for offline SIEM ingest
  • Timestamp source: local hardware clock or GPS receiver
  • Log fields: user, action, source, target, checksum, status

USB Device Policy Enforcement

  • USBGuard: whitelist only approved transfer devices
  • usbguard allow-device <device-id>
  • Block all USB storage by default on target hosts
  • Approved devices: IronKey D500S, Apricorn Aegis only
  • Audit: all USB insert/remove events logged
  • Auto-lock: device auto-locks after transfer completes

Write-Blocker Integration

  • Forensic write-blockers for source media verification
  • Tableau T356789iu or CRU WiebeTech models
  • Ensures source VMware disks are not modified during export
  • Required for: evidence preservation, classified data handling
  • h2kvmctl reads source in read-only mode by default
  • Verification: compare source checksums pre/post export

Deployment Architecture Patterns

Four proven patterns for air-gapped KVM/KubeVirt deployment.

Pattern 1: Single-Host Portable Lab

  • Use case: Field deployments, mobile command, SCIF
  • Hardware: ruggedized server (Dell R660xs or HPE DL360)
  • OS: Rocky 9 STIG-hardened, FIPS enabled
  • Storage: 2x NVMe in RAID 1, LUKS encrypted
  • VMs: 5-15 per host, all local storage
  • Migration: USB transfer, single h2kvmctl run
  • Recovery: full host image on encrypted USB backup
  • Cost: $8K hardware + $0 software

Pattern 2: Multi-Host Sneakernet Sync

  • Use case: Air-gapped data center, 50-200 VMs
  • 3-5 hosts with shared NFS or local LVM storage
  • Sneakernet sync: export VM changes to USB weekly
  • Pacemaker HA cluster (no network to external)
  • Local DNS/DHCP/NTP within air-gapped network
  • Migration waves: 10-20 VMs per transfer cycle
  • Dedicated migration host processes imports
  • Cost: $40K hardware + $13K RHEL

Pattern 3: Air-Gapped K3s + KubeVirt

  • Use case: Modern workloads, containers + VMs
  • K3s lightweight Kubernetes (single binary, 50MB)
  • KubeVirt for VM workloads alongside containers
  • Longhorn for replicated storage (no Ceph complexity)
  • Harbor registry for air-gapped container images
  • All images pre-loaded via USB transfer
  • GitOps with local Gitea (no GitHub/GitLab cloud)
  • Cost: $50K hardware + $0 software

Pattern 4: Cross-Domain with Data Diode

  • Use case: UNCLASS → SECRET transfer, IC networks
  • Data diode: Owl DualDiode or Waterfall Unidirectional
  • Export side: h2kvmctl streams to diode sender
  • Receive side: h2kvmctl reassembles from diode receiver
  • One-way: physically impossible to reverse data flow
  • Automated: scheduled transfers without manual USB
  • Bandwidth: 1-10 Gbps depending on diode model
  • Cost: $80K-$200K diode + infrastructure

Recommended: Pattern 2 for Most Air-Gapped Environments

Multi-host with sneakernet sync provides the best balance of capability, cost, and security. Start with Pattern 1 for POC, graduate to Pattern 2 for production. Pattern 3 for organizations with container strategy. Pattern 4 only when continuous cross-domain transfer is mandated.
