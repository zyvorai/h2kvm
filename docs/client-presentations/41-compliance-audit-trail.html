Common Auditor Questions

Questions About the Migration

  • "How do you ensure data integrity during conversion?"
  • "What change control process was followed?"
  • "How were VMs tested before production cutover?"
  • "What is the rollback procedure if migration fails?"
  • "Who approved the change and when?"
  • "Were duties separated (dev/test/deploy)?"

Answers (with h2kvmctl evidence)

  • SHA-256 checksums pre/post conversion (manifest.json)
  • Change ticket + approval in ITSM (reference in migration log)
  • Boot test + smoke test results (automated, logged)
  • VMware VMs kept 48 hours; rollback = power on VMware VM
  • Approval signatures in change ticket (linked in config YAML)
  • CI/CD pipeline: validate→convert→test→deploy with approval gates

Separation of Duties

Requester (Migration Lead) != Approver (CAB/Manager) != Implementer (Migration Engineer) != Verifier (QA/App Owner). For SOX compliance, no single person should request, approve, implement, and verify a change. h2kvmctl CI/CD pipelines enforce this with role-based approval gates.

HIPAA Migration Controls

Protecting electronic Protected Health Information (ePHI) during migration.

HIPAA Safeguard Mapping

Administrative Safeguards

  • 164.308(a)(1): Risk analysis — migration risk assessment completed before RFC
  • 164.308(a)(5): Security awareness — migration team briefed on ePHI handling
  • 164.308(a)(6): Incident response — plan for migration failure with ePHI exposure
  • 164.308(a)(8): Evaluation — post-migration security evaluation within 30 days
  • Evidence: Risk assessment doc, training records, incident response plan, evaluation report

Technical Safeguards

  • 164.312(a): Access control — only authorized personnel access ePHI VMs during migration
  • 164.312(b): Audit controls — all access to ePHI systems logged
  • 164.312(c): Integrity — SHA-256 checksums verify data not altered
  • 164.312(d): Authentication — SSH keys + sudo, no shared accounts
  • 164.312(e): Transmission security — encrypted transfer (TLS/SSH)
  • Evidence: audit.log, checksums.json, SSH key list, encryption verification

Physical Safeguards

  • 164.310(a): Facility access — data center access log during migration
  • 164.310(c): Workstation security — migration console in secured area
  • 164.310(d): Device controls — secure media handling for USB transfers
  • Evidence: Badge access logs, workstation inventory, media disposal records

CDE Scope During Migration

During migration, both VMware and KVM environments are in PCI scope until VMware VMs are fully decommissioned. Minimize this dual-scope period by migrating CDE VMs in a single wave with immediate VMware decommission. Document the scope reduction in your next PCI-DSS assessment.

Log Integrity Protection

  • Forward to SIEM in real-time (rsyslog → Splunk/ELK)
  • Hash chain: each log entry includes hash of previous
  • Write-once: logs on append-only storage or WORM
  • Rotation: logrotate with SHA-256 checksums per file
  • Retention: 12 months (PCI-DSS), 6 years (SOX), 6 years (HIPAA)
  • Access: read-only for auditors, append-only for system
