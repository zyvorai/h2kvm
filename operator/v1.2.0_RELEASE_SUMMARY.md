### 3. CLI Tool (h2kctl)

**Purpose**: Command-line interface for easier management

**Commands** (5 total):
- `h2kctl migrate` - Create HyperConversion resources
- `h2kctl list` - Display migrations in table format
- `h2kctl describe` - Show detailed resource info
- `h2kctl logs` - Stream logs from migration pods
- `h2kctl delete` - Remove resources
- `h2kctl version` - Display version info

**Examples**:
```bash
# Quick migration
h2kctl migrate disk.vmdk --vm-name my-vm --cpu 4 --memory 8Gi

# With cloud-init
h2kctl migrate disk.vmdk --vm-name ubuntu --cloud-init cloud-init.yaml

# With additional disks
h2kctl migrate disk.vmdk --vm-name db-server \
  --disk name=data,source=blank,size=50Gi \
  --disk name=backup,source=http://example.com/backup.qcow2

# Monitor
h2kctl list -n default
h2kctl logs my-migration -f
```

**Impact**: +2% User Experience, +1% Overall

### 4. Multi-Disk VM Support

**Purpose**: VMs with multiple storage volumes beyond root disk

**Disk Source Types** (3):
1. **Blank Disk** - Empty disk to be formatted
2. **URL Source** - Import from HTTP/HTTPS/S3
3. **Existing PVC** - Clone or reference existing volume

**Features**:
- Boot order configuration (root=1, additional=2,3,4...)
- Bus types: virtio (default), sata, scsi
- Per-disk StorageClass selection
- Parallel DataVolume creation
- Status tracking with additionalDiskDataVolumes map

**Example - Database Server**:
```yaml
spec:
  vm:
    additionalDisks:
      - name: postgres-data
        source: { blank: true }
        size: 500Gi
        storageClass: nvme-ssd
        bootOrder: 3
      - name: postgres-wal
        source: { blank: true }
        size: 100Gi
        storageClass: fast-ssd
        bootOrder: 4
      - name: backups
        source: { blank: true }
        size: 1Ti
        storageClass: hdd
        bootOrder: 5
```

**Impact**: +1% Deployment, +1% Overall

## 🎯 Use Cases

### Simple VM Migration (80% use case)

**Scenario**: Migrate VMDK disk from VMware to KubeVirt

```yaml
apiVersion: h2kvm.io/v1alpha1
kind: HyperConversion
metadata:
  name: simple-migration
spec:
  source:
    url: "https://storage.example.com/vm-disk.vmdk"
    format: vmdk
  storage:
    storageClass: local-path
    size: 20Gi
  vm:
    name: migrated-vm
    cpu:
      cores: 2
    memory: 4Gi
```

### Multi-Disk Database VM

**Scenario**: PostgreSQL server with separate data, WAL, and backup volumes

```yaml
spec:
  source:
    url: "https://storage.example.com/postgres-base.qcow2"
  vm:
    name: postgres-server
    cpu: { cores: 8 }
    memory: 16Gi
    additionalDisks:
      - name: data
        source: { blank: true }
        size: 500Gi
        storageClass: nvme-ssd
      - name: wal
        source: { blank: true }
        size: 100Gi
        storageClass: fast-ssd
      - name: backup
        source: { blank: true }
        size: 1Ti
        storageClass: hdd
```

### Cloud-Init VM Deployment

**Scenario**: Ubuntu server with pre-configured users and packages

```yaml
spec:
  source:
    url: "https://cloud-images.ubuntu.com/jammy/current/jammy-server-cloudimg-amd64.img"
  vm:
    name: ubuntu-server
    cloudInit:
      configMapRef:
        name: ubuntu-init  # References cloud-init template
```

## 📈 Comparison: HyperConversion vs MigrationJob

| Feature | HyperConversion | MigrationJob |
|---------|----------------|--------------|
| **Target Use Case** | Simple, common workflows | Enterprise migrations |
| **Disk Upload** | CDI DataVolume (HTTP/S3) | CDI + Python workers |
| **Offline Fixes** | Optional (via Python workers) | Full support (fstab, grub, etc.) |
| **Batch Operations** | Single VM | Batch processing |
| **Networking** | Standard KubeVirt | Advanced Multus/SR-IOV |
| **Complexity** | Low (opinionated) | High (configurable) |
| **Implementation** | Go controller | Python Kopf operator |
| **Best For** | Quick migrations | Complex enterprise scenarios |

**Recommendation**: Use HyperConversion for 80% of migrations. Use MigrationJob for complex scenarios requiring offline fixes and batch processing.

## 🔧 Technical Architecture

### Workflow

```
HyperConversion CR
       ↓
  [Pending Phase]
       ↓
  Create CDI DataVolume ────> HTTP/S3 Source
       ↓
  [Uploading Phase] ────> Monitor Progress (0-100%)
       ↓
  Upload Complete
       ↓
  [CreatingVM Phase]
       ↓
  Create KubeVirt VM ────> References DataVolume
       ↓
  [Ready Phase]
```

### Components

- **HyperConversion CRD**: Defines desired state (source, storage, VM config)
- **Controller**: Phase-based state machine orchestrating workflow
- **CDI Helper**: Manages DataVolume creation and status monitoring
- **KubeVirt Helper**: Builds and creates VirtualMachine resources
- **Status Manager**: Tracks progress and updates conditions
- **CLI Tool**: User-friendly command-line interface

### RBAC Permissions

- `hyperconversions.h2kvm.io`: Full CRUD
- `datavolumes.cdi.kubevirt.io`: Full CRUD
- `virtualmachines.kubevirt.io`: Full CRUD
- `events`: Create, patch
- `pods`: Get, list, watch (for worker jobs)
